## 已完成

### M0：core 和命令行

**关键设计决定**

- **严格复刻 `load_vendor_configs_from_json` 的顺序语义**：每个厂商单独加载，每一类有自己的名字表，按清单顺序一次扫描完成。不按名字构建全局继承图，否则「父项排在子项后面」这类会让 OrcaSlicer 加载失败的错误就会被掩盖。
- **厂商顺序**：OrcaFilamentLibrary 排第一，其余按字母排序。OrcaSlicer 用的是目录遍历顺序，标准没有规定，这里排序是为了结果可重现。
- **加载从不中断**：所有偏差都记成 `Issue`，分 `fatal` / `error` / `warning` / `info` 四级。`fatal` 专门表示「OrcaSlicer 会因此拒绝加载整个厂商」，这样校验结果和 OrcaSlicer 的实际后果能一一对应。
- **值一律按字符串处理**：`RawValue` 只有字符串和字符串数组两种形态，和 JSON 里的写法一致；类型信息留给后来的 schema（M0.5）。
- 查找用文件里的 `name`，不用清单名或文件名；元信息键名不区分大小写，和 `boost::iequals` 一致；容忍 UTF-8 BOM，但会记一条问题。
- OrcaFilamentLibrary 的清单为空时，按 OrcaSlicer 的规则扫描磁盘生成清单。
- **回归测试锁定 OrcaSlicer `953509c23f` 的统计数字**，并用独立的 Python 参考脚本交叉验证。数据变化时需要有意识地更新这些数字。

### M1：桌面浏览器

**关键设计决定**

- **锁定 `gpui-kit = "=0.8.0"`**：它还没到 1.0，版本之间有破坏性改动。遇到 API 问题时去读 `~/.cargo/registry` 里的源码，不靠猜。
- **加载放在后台线程**：`Repository::load` 和 `Catalog::new` 都在后台执行器上跑。`Catalog` 是只给界面用的索引，包括按厂商分组和每个预设的问题。`TreeItem` 里有 `Rc`，不是 `Send`，所以树节点要回到前台再构建。重新加载时，新结果会覆盖旧结果。
- **树是虚拟化的**：节点 id 里编码了 `Node`（厂商、分组、机型、预设），渲染回调可以直接从 id 还原节点。
- **界面用 headless 测试验证**：这个环境没有录屏权限，截不了窗口。测试用 `#[gpui_kit::test]` 渲染真实界面、模拟点击，再断言状态和元素属性。
- 图标用 `gpui_kit::assets::IconName`，即完整的 Lucide 图标集，应用里注册了 `AllAssets`。

### M0.5：配置项 schema

> M16 起整体移除：schema、值校验、`handle_legacy` 移植和默认值层都已删除，以下为当时的记录。

**关键设计决定**

- **导出程序放在 OrcaSlicer 仓库里**：`src/dev-utils/Snapmaker_Orca_schema_export.cpp`，在 `personal/schema-export` 分支上。它必须链接 libslic3r 才能遍历 `print_config_def`。生成的 `schema.json` 复制到本仓库的 `crates/profile-core/schema/`，用 `include_str!` 内嵌，文件里记录生成时的 `source_commit`。
- **导出三类默认预设的完整内容，而不只是每个配置项的默认值**：默认预设（`PresetBundle` 构造函数里建的那几个）就是「没有 `inherits` 的预设」的起点，其中有几项没法从单个配置项的默认值推出来：多出的 `*_settings_id` 键，以及耗材里被置为 `nil` 的 nullable 值。
- **「哪些键属于哪一类」以默认预设的键为准**：这是 `Preset::remove_invalid_keys` 实际的判断依据，`Preset::*_options()` 列表只是参考。
- **绕开 OrcaSlicer 的一个空指针问题**：`coEnums` 类型的默认值是不带 `keys_map` 的 `ConfigOptionEnumsGeneric`，直接调 `vserialize()` 会段错误。导出程序改用配置项定义里的枚举表来写值。
- **`handle_legacy` 只能手工移植**（`legacy.rs`）：这些规则是代码，不是数据，导不出来。实现时要注意，数组值会经过两次 `handle_legacy`：第一次值为空，只用来确定键名；第二次用拼接后的值。
- **严重级别按 GUI 实际的加载规则 `EnableSystemSilent` 来定**：
  - 标量数值完全解析不了：`fatal`，整个厂商加载失败；
  - 枚举值或布尔值不合法：`error`，会被静默替换成默认值；
  - vector 元素解析不了：`error`，会被读成 0；
  - 数值后带多余文字、非 nullable 数组里有 `nil`、超出界面上的取值范围：`warning`；
  - 未知键：`warning`，OrcaSlicer 会静默忽略；
  - 过时键、改了名的旧键：`info`。
- **`Repository::load` 的行为保持不变**，另外新增 `load_with_schema`。值的来源用 `Origin` 表示，`Origin::Default` 代表来自 schema 的默认预设。
- **性能**：字符串数组（主要是 G-code）不拼接也不转义，因为没有任何检查会用到它们。加上 schema 后，全量加载从约 195 ms 增加到约 230 ms。
- **只报告，不修 OrcaSlicer 的配置数据**：检查发现的数据问题只作为结论报告，这是用户的决定。

### M2：继承链视图

> M16 起没有默认值层，类别 / 名称列改为只显示键名。

**关键设计决定**

- **`Repository::trace(id)`**：对每个键返回继承链上设置过它的所有层，离预设最近的在前，第一层就是最终值。这是界面「来源层」和「被覆盖的值」的数据来源，后续的 M4 对比也可以直接复用。
- **`IssueKind::key()`**：把校验问题挂到对应的键上，界面可以按键显示问题。
- **预设详情分成 Overview 和 Values 两个标签页**：Values 是一个 `DataTable`，选中某一行时，下方面板列出每一层的值，以及配置项的说明和问题。
- **`ValuesView` 在需要时才创建**：`TableState` 和 `InputState` 的构造需要 `Window`。最初在 `render` 里创建，因为当时树的选择回调里拿不到 `Window`；M5 之后 `StudioApp::new` 有了 `Window`，改为在事件处理函数里创建（`observe_in` 的选择回调、切换标签页、命令面板跳转），符合 gpui-kit Coding Guides「不在 render 里改状态」的要求。值编辑器同样改为在选择或数值变化的处理函数里重建。
- **表格 delegate 持有一份自有的显示行（`ValueRow`）**，不借用 `Catalog`，免得出现自引用的生命周期问题。筛选之后，按键名找回原来选中的那一行。
- 默认排序是先按 schema 的类别、再按配置项名称，schema 里没有的键排在最后。
- **测试经验**：
  - 表格行用 `("row", ix)` 查找；
  - 标签页要在 `within("preset-tabs")` 里按序号点击；
  - 点击触发订阅事件之后，要先 `run_until_parked`，再 `render_frame`，然后才能断言。

### M3：编辑表单

> M16 起控件只按值的形态选择（单行、每行一项、多行），不再有勾选框和枚举下拉。

**关键设计决定**

- **按字节范围改写文件，不重新序列化**（`document.rs`）：`Document` 记下每个顶层成员值的字节范围，修改时只替换这一段，新键追加在最后一个成员之后。缩进、BOM、文件末尾有没有换行都保持原样。
  - 替换数组时沿用原值的写法：单行数组保留单行和原来的分隔符（`", "` 或 `","`）；多行数组沿用原来的元素缩进和右括号缩进。新键用文件自己的缩进，按 nlohmann 的多行写法。
  - 字符串转义用 serde_json，和 nlohmann::json 的 `dump()` 完全一致。现有数据里只用到 `\n`、`\"`、`\\`、`\t`，没有 `\u`。
  - 设成和原来相同的值时不改动文本，所以「打开 → 不修改 → 保存」得到的字节和原文件完全相同。
  - 对现有数据的验证：把全部 7935 个文件里的约 19 万个值逐个按原写法重新渲染，只有 4 个数组和原文不同，而且差别只在空白（`[` 或元素后面多余的空格、空数组里的空白行）。测试把这 4 处固定下来。
- **编辑会话**（`edit.rs` 的 `EditSession`）：在预设自己的值上叠加修改，撤销栈记录每一步的前后值。值为 `None` 表示删掉这个键、恢复成继承来的值。`Repository::trace_with` 和 `check_values` 直接基于会话里的值计算，所以表格、来源层和校验问题都会实时反映修改。
- **保存的安全措施**：
  - 保存前把磁盘上的文件和会话最后一次加载或保存的值比对，不一致就拒绝保存（`SaveError::ChangedOnDisk`），绝不覆盖外部的修改；
  - 先写到同目录下的临时文件再改名，失败时不会留下写了一半的文件；
  - 只有用户在确认面板里点「Save N file(s)」才写盘，确认面板会列出每个预设、每个键的前后值。
- **M3 当时不自动重新加载**：避免丢失其他预设的编辑；M8 已加入会话迁移，保存后自动刷新子孙预设。
- **编辑放在下方的详情面板里**：gpui-component 的 `TableDelegate` 不支持单元格内编辑。控件按 schema 类型选择：
  - bool：复选框；
  - enum：下拉框。可选值取自 `enum_keys`，也就是加载时接受的值，显示名用 `enum_values` / `enum_labels`。Snapmaker 特有的 `enum_values_u1` / `enum_values_ex` 只有 `curr_bed_type` 用到，而且只影响界面显示，所以不采用；
  - 单个值：单行输入框，按回车或点 Apply 生效；
  - 数组：多行文本框，一行一个元素；
  - G-code 等多行字符串：多行文本框，内容原样编辑。由多个多行元素组成的数组，一个文本框表示不了，只提示到文件里去改。
  - **修改保持值原来的形态**：字符串还是字符串，单元素数组还是数组（现有数据里有 74880 个单元素数组），这样 diff 只有值本身的变化。
- **编辑状态放在应用层的 `Edits` 实体里**：每个预设一个会话。切换预设不会丢失编辑，树上会给有未保存修改的预设加铅笔图标。M3 的重新加载和打开目录都采用两次点击的丢弃确认；M8 已让 Reload 保留会话，仅 Open 切换目录仍需确认。
- **快捷键**：⌘Z 撤销、⇧⌘Z 重做、⌘S 打开保存确认，作用范围是 `ValuesView`。焦点在输入框里时，输入框自己的撤销优先。

### M4：预设对比

**关键设计决定**

- **`Repository::diff` / `diff_with`**：对两个同类型预设的 `trace` 求键并集，保留两边完整的继承层；支持跨厂商，类型不同返回 `DiffError`。`diff_with` 接受两边各自的编辑会话值，祖先仍使用加载时的快照，与 Values 页一致。
- **按原始有效值比较**：使用 `RawValue` 相等性，区分字符串和数组、数组元素顺序以及数值字符串的写法。缺失值不同于空字符串或空数组。来源不参与值是否相等的判定，但两边来源都保留。
- **入口采用 Values 页的「Compare with…」**：可搜索的选择器只列出其他同类型预设，包含模板和跨厂商预设，显示厂商、名称和路径以区分重名。此阶段采用这个入口，树的右键快捷入口留待后续交互完善。
- **独立的只读 `CompareView`，沿用 Values 的表格与来源层展示方式**：列出类别、名称、键、左右值和左右来源，默认只看差异，可以搜索和排序，选中键后查看两边的继承链。数组显示方括号，避免把数组和字符串的差异隐藏掉。
- **观察共享的 `Edits` 实体**：任一边的编辑变化都会刷新对比；标题标明未保存修改。返回 Values 后保留编辑器、筛选和选择，对比本身不写文件。
- **Headless 测试验证实际交互**：选择器搜索、选择预设、差异筛选、来源展开、编辑刷新和返回 Values。选择器根节点会填满父容器，需显式限制高度，避免挤掉表格。
- **真实数据验收**：`Generic ABS @U1 0.2 nozzle` 对比 Snapmaker 的 `Generic ABS`（实际的 0.4 nozzle 预设名），最终值仅 `compatible_printers` 不同。core 回归测试与 headless 界面测试均覆盖这一案例。

### M5：全局搜索和命令面板

> M16 起配置项只按键名搜索。

**关键设计决定**

- **线性扫描，不建倒排索引**（`search.rs` 的 `SearchIndex`）：所有预设文件里写的值一共约 25 万个、7.5 MB 文本。索引只存小写副本，加载时在后台和 `Catalog` 一起构建；release 构建下建索引约 37 ms，每次查询 2–3 ms，所以每输入一个字符就同步搜一次，不需要后台查询。
- **搜三类内容**，查询里的每个词都必须出现（不区分大小写）：
  - **预设**：名称、别名、`setting_id`、`filament_id`（用 `Repository::filament_id`，和 OrcaSlicer 的取值顺序一致）。排序：名称以查询开头的在前，可选预设在模板前，名称短的在前；
  - **配置项**：schema 里的键名和名称；
  - **值**：只搜文件里直接写的值，不搜继承来的和默认值，否则每个值会在所有子孙预设里重复出现。匹配的文本是 `key = value`，所以 `nozzle_temperature 270` 能找到「哪些文件把它设成 270」。结果片段保留原文的大小写，多行内容压成一行。
- **只搜加载时的数据**：未保存的编辑不在索引里；M8 已实现保存后自动重建索引。
- **一个面板同时放命令和搜索结果**：用 gpui-component 的 `Command`，设 `filterable(false)`，由应用根据 `on_query` 自己生成分组：Commands、Presets、Options（只在选中了预设时出现）、Values set in files，每组最多 8 条，标题里显示总数。`on_confirm` 给出的 `IndexPath { section, row }` 对应到应用记下的目标；空的分组不显示，所以目标表和分组是一起生成的。
- **面板放在 `Root` 的对话框里**（`window.open_dialog`）：遮罩、焦点锁定、Esc 和点击外部关闭、关闭后恢复原来的焦点，都由 `Root` 负责，符合 gpui-kit Coding Guides 对模态层的要求。对话框的构建函数可能被反复调用，所以它只读取应用里的数据，初始聚焦用一次性的标记。
- **不在 render 里改状态**：分组和目标表在打开面板时和查询变化时（`on_query`）重新生成，render 只读取。debug 构建下一次搜索约 30 ms，放在 render 里会随每次悬停重复执行。
- **跳转**：`TreeState::set_selected_item` 会展开所有上级节点并选中，`reveal_item` 再滚动到这一行；跳到值或配置项时切到 Values 页，把表格筛选到这个键并选中。
- **快捷键需要焦点**：没有任何元素获得焦点时，⌘K 不会被分发。`StudioApp::new` 现在接收 `Window`，创建时把焦点给根元素，并用 GPUI 的 `on_focus_lost` 在焦点所在的元素消失（比如重新加载后视图被替换）时把焦点收回根元素，而不是在 render 里请求焦点。
- 命令行也有 `profile-tool search <查询>`，输出三类结果和耗时。

### M6：校验结果面板和条件表达式

> M16 起条件变量按值的文本推断类型，不再取 schema 默认值；与 OrcaSlicer 的对照仍为 0 处差异。

**关键设计决定**

- **条件表达式只实现用得到的那部分语法**（`condition.rs`）：现有数据里有 97 个工艺预设、29 种不同的条件，全部来自 Prusa，只用到变量、`[下标]`、`=~` / `!~` 正则、`==` 和 `and`。实现时补齐了 `PlaceholderParser` 布尔表达式这一层：`or`/`||`、`and`/`&&`、`not`/`!`、括号、`==`、`!=`/`<>`、`<`、`>`、`<=`、`>=`、字符串、`true`/`false`。四则运算和 `if` 块不支持，遇到时报「无法解析」。
- **语义对照 C++ 源码**：
  - `=~` 是 `boost::regex_match`，必须匹配**整个**字符串；Boost 默认的 Perl 语法里 `.` 也匹配换行，而 40 个带 `PRINTER_…` 的打印机 `printer_notes` 全是多行。所以正则编译成 `(?s)^(?:pattern)$`；
  - `==` 比较两个数时，只要有一边是浮点数就按 1e-8 的容差；两边有字符串时按字符串比较；布尔值只能比较相等；
  - `and` / `or` 两边都会求值，和 C++ 一致。
- **变量**：取目标预设的最终值（包括 schema 默认值），按 schema 的类型转成布尔、整数、浮点数或字符串；打印机额外提供 `printer_preset` 和 `num_extruders`，和 `is_compatible_with_printer` 一致。vector 不带下标、下标越界、未知变量都是求值错误。
- **兼容性规则**（`compat.rs` 的 `CompatibilityIndex`，加载完成后构建一次，存在 `Repository` 里）：按规格文档第 6 节的顺序判断，结果带上原因（`Verdict`：被排除、条件、在列表里、不在列表里、没有限制）。条件只在 `compatible_printers` 为空时生效；条件出错时按 OrcaSlicer 的做法视为兼容。公共耗材库的排除机制按别名匹配，同一别名有多个库耗材时取最后一个，和 C++ 的 map 写法一致。也支持耗材与工艺之间的 `compatible_prints` / `compatible_prints_condition`（现有数据没有用到）。
- **条件出错记成问题**：解析失败是 `condition-invalid`，对部分预设求值失败是 `condition-failed`（附第一个失败的例子和失败数量），级别都是 error。现有数据里两者都是 0。
- **性能**：先测再优化。加了兼容性计算和条件检查后，release 加载从约 230 ms 到约 265 ms，没有为此加缓存。界面里预设的兼容性摘要在选中预设时计算一次，不在 render 里算。
- **问题面板放在窗口底部**：按 gpui-kit Design Guides 的「先从任务出发」，主任务是在全部问题里筛出要紧的，再跳到对应的预设和键。面板是可调高度的底部区域（类似 IDE 的 Problems），上方的树和详情跟着选中的问题变化。
  - 筛选：最低严重级别（默认「warning 及以上」，因为 4105 条 info 大多是过时键之类的噪音）、问题代码、厂商，都是 `Select`，代码和厂商可搜索并带数量；另有文本筛选。
  - 选中一行（点击或方向键）就跳到对应的预设；问题涉及某个键时打开 Values 页并定位到这个键。键盘焦点留在列表里，可以一直用 ↑↓ 浏览。没有对应预设的问题（比如孤立文件）跳到厂商节点。
  - 严重级别同时用图标和文字表示，不只靠颜色；入口是工具栏的「Issues」按钮（打开时显示为选中状态）和命令面板的「Show issues」。
- **兼容性显示在预设的 Overview 里**：耗材和工艺显示条件（如果有）和兼容的打印机（前 12 个加剩余数量）；打印机显示兼容的工艺和耗材数量。命令行有 `profile-tool compat <预设名>`，列出每台打印机兼容的原因。
- **和 OrcaSlicer 逐项对照，结果完全一致**（经用户同意，在 OrcaSlicer 仓库加了工具）：
  - `Snapmaker_Orca_compat_export`（OrcaSlicer `personal/schema-export` 分支，`src/dev-utils/`）按 GUI 的方式加载系统配置：临时的 data_dir 里放一个指向 profiles 的 `system` 符号链接，用 `EnableSystemSilent` 规则调用 `load_presets`，不会往 OrcaSlicer 检出目录写任何文件。然后对每个系统耗材和工艺，用 OrcaSlicer 自己的 `is_compatible_with_printer` 判断它和每台系统打印机是否兼容，导出成 JSON；
  - `profile-tool compat-check <表>` 拿这张表和 `CompatibilityIndex` 逐项比较，报告两边各自多出的打印机、预设和不一致的兼容集合，有差异时退出码为 1。两个厂商重名的预设（BBL 和 Snapmaker 的 10 个），OrcaSlicer 只保留一个，比较时接受任一个；
  - 在 OrcaSlicer `953509c23f` 的数据上：796 台打印机、2906 个耗材、2156 个工艺，约 400 万个（预设，打印机）组合，**0 处差异**。故意改动表里的三处后，`compat-check` 能把三处都报出来，说明比较本身有效；
  - 这张表约 700 KB，没有提交进仓库。回归测试固定的是本实现在真实数据上的几个结果（例如 Snapmaker U1 0.4 兼容 16 个工艺、169 个耗材，库里的 Generic ABS 对 796 台打印机中的 68 台被排除），OrcaSlicer 更新后按 AGENTS.md 里的命令重新导出、对照。

### M7：布局、主题、多窗口

**关键设计决定**

- **不引入 Dock**（用户决定）：窗口只有三个职责固定的区域（导航树、详情、问题面板），gpui-kit Design Guides 只在「用户需要自由摆放许多长期存在的工具或文档」时才建议用 Dock，而引入它要把 `StudioApp` 拆成多个面板实体。改为保存和恢复现有布局，路线图原来写的 Dock 方案不做。
- **设置文件**（`settings.rs`）：`~/Library/Application Support/orca-profile-studio/settings.json`（其他平台用 `XDG_CONFIG_HOME` 或 `~/.config`），可用环境变量 `ORCA_STUDIO_SETTINGS` 指定别的路径。所有窗口共用一个 GPUI 全局 `SettingsStore`，每次改动立刻经临时文件改名写盘；文件不存在或损坏时用默认值，未知字段被忽略，所以别的版本写的文件也能读。保存的内容：
  - 主题偏好；
  - 上次加载的目录（启动时的顺序：命令行参数、`ORCA_PROFILES_DIR`、上次的目录、旁边的 OrcaSlicer 检出）；
  - 侧栏宽度、问题面板是否打开和高度：两个可调分隔都改用保留的 `ResizableState`，在它发出 `Resized` 时保存，启动时作为面板初始尺寸恢复；
  - 窗口大小：在窗口关闭时（`on_window_should_close`）保存，新窗口按它打开。
- **主题**：偏好有三种，System（默认，跟随系统，运行中系统切换也会跟着变，用 `observe_window_appearance`）、Light、Dark；在命令面板里用「Theme: …」切换，当前项打勾。颜色全部来自 `cx.theme()` 的语义 token，所以切换后整个界面一起变。
- **多窗口，各自独立**（用户决定）：⌘N、File 菜单的「New Window」或命令面板都会打开一个新窗口，它加载上次的目录，自己维护加载结果和编辑会话。两个窗口改同一个文件时，后保存的会因为 `ChangedOnDisk` 被拒绝，不会互相覆盖。最后一个窗口关闭时才退出应用（原来是关闭任意一个窗口就退出）。
- **加载改用 `spawn_in`**：加载完成的回调能拿到 `Window`，这样上次打开着的问题面板能在加载后重新创建。
- **测试**：切换主题后背景色确实变化；布局按设置恢复，模拟拖动（`resize_panel`，和拖动一样发出 `Resized`）、关闭问题面板、加载目录后，设置文件里的值随之更新；「New window」命令打开第二个窗口。测试里的设置默认只在内存中（`open_with_settings(…, None)`），不会写用户的设置文件。

### M8：保存后自动刷新

**关键设计决定**

- **后台全量加载、统一替换**：保存成功后由 `EditsEvent::Saved` 通知窗口重新加载 `Repository` 和 `Catalog`，继承、问题、兼容性、搜索都从同一份新快照读取。跨厂商继承 OrcaFilamentLibrary 的耗材自然一起更新。部分保存成功后遇到失败，也触发刷新，并保留具体失败信息。
- **刷新期间保留旧视图**：树、Values 和编辑器继续可用，工具栏显示刷新状态。完成时读取当时的选择和编辑会话，因此加载期间的导航和新编辑也能保留。请求编号防止旧结果覆盖新请求；每次保存都会发起新的加载，所以读取期间再次保存产生的混合快照也会被请求编号丢弃。
- **按文件路径迁移会话**：`Edits::rebase` 把文件对应到新的 `PresetId`，`EditSession::rebase` 校验新加载的值是否等于最后加载或保存的基线，保留当前值及完整的 undo / redo 栈。保存本身不清空历史，撤销到保存前的值会重新变成未保存修改。
- **保留浏览状态**：树的预设、机型和厂商按文件路径重新定位，保留原来展开的节点（包括收起的父节点里展开的子节点），并选中原来的节点；保留当前标签页。Values 复用原来的实体和控件，保留筛选、排序、选中的键及尚未应用的输入。对比页保留两边对象、筛选、排序和选中的键；问题面板更新数据与选项，保留仍有效的筛选和排序；已打开的命令面板按原查询重建结果。
- **Reload 不再丢弃编辑**：和保存后的刷新走同一条路径。Open 切换到不同目录仍沿用原来的丢弃确认。
- **外部冲突不自动合并**：有未保存修改的文件出现参数、元信息变化，或文件被删除、无法加载时，暂停整次快照替换；已保存、只剩历史记录的会话遇到这些变化时直接丢弃历史、采用磁盘版本，不阻塞刷新。冲突时保留旧数据和所有会话，避免一部分视图使用新数据、一部分使用旧数据。窗口中的持久提示可打开 `Root` 的 `AlertDialog`，逐项列出路径和原因：恢复文件后重试，或明确放弃这些文件的编辑和历史后采用磁盘版本；其他会话保留。取消和 Escape 都不丢弃编辑。仅排版变化不算参数冲突，保存仍保留磁盘格式。
- **错误在窗口中可见**：目录加载失败保留旧视图并提示重试；部分保存显示已保存数量和失败文件。磁盘写入冲突检查继续有效。
- **测试**：core 覆盖基线迁移、保存前后撤销/重做、外部改动拒绝迁移；headless 界面测试覆盖保存父项后子项更新、加载期间的新编辑、跨厂商公共库继承、搜索/问题/兼容性更新、编号变化后的定位和正确保存、对比状态保留、外部改动和删除、失败重试、部分保存以及冲突确认的点击/Enter/Escape。所有写盘测试只使用临时 fixture，测试窗口启用减少动态效果以稳定弹窗交互。

- 依据 `gpui-kit-design-guides/references/design-guides.md` 的完整指南和 `gpui-kit/references/coding-guides.md`，检查应用代码及锁定的 gpui-kit 0.8.0 源码。

**Design review checklist（逐项结论）**

| 条目 | 结论 |
|---|---|
| 1. 任务是否清楚 | 按预设浏览→查看来源→编辑→预览保存的主路径保持；空目录、无选择、无匹配及错误均有说明 |
| 2. 操作是否兑现标签承诺 | Save 打开预览，默认提交才写盘；Open 说明目标和丢弃范围；Reload 保留编辑；关闭/退出先确认。有点击/键盘及磁盘断言 |
| 3. 层级是否克制 | 工具栏取消 primary，普通章节不自动全大写；警告仅用于异常状态，默认提交由标准对话框强调 |
| 4. 能否减少不必要界面 | 移除双击式丢弃警告和内联保存确认状态，复用标准 AlertDialog；无新导航层级 |
| 5. 结构是否精确 | rem 排版；Pixels 仅用于窗口、表格列、Resizable 和 Dialog API。测试检查控件边界、表格/编辑器不重叠；像素级对齐和滚动条视觉位置待人工检查 |

| 7. 所有状态和约束下是否可用 | 已覆盖无匹配、冲突、保存/加载失败、错误重试、减少动态效果、窄窗口和字号扩大；取消保持状态。中文界面属于 M12，真实长文本与显示缩放待人工检查 |

**Accessibility checklist（逐项结论）**

| 条目 | 结论 |
|---|---|

| 焦点顺序符合任务顺序 | 由组件树的自然顺序管理；确认面板改为模态焦点范围，不再夹在详情滚动区 |
| 焦点可见、关闭浮层后恢复 | 沿用标准组件焦点环，修复控件被替换后的祖先恢复；Escape 后可继续 ⌘S/编辑已有测试。真实焦点环对比度未测量 |

| 文字和边界对比度充分 | 源码全部使用语义主题色；亮/暗主题切换测试通过。真实窗口及自定义主题对比度未测量 |

**平台限制与后续事项**
- GPUI 0.3.9 的 `on_app_quit` 发生在无法取消的 shutdown 阶段。当前保护覆盖原生窗口关闭、⌘W、应用菜单 Quit 和 ⌘Q；Dock/操作系统直接终止、强制退出不在可拦截范围。完整系统退出拦截需要上游提供可取消的 quit-request API，未修改依赖或 OrcaSlicer 仓库。
- 首个窗口创建失败时没有 Root 可显示通知，会尝试系统通知并保留 stderr。系统通知依赖平台授权；macOS 的普通 `cargo run` 不保证系统通知投递，需要受信任的 `.app`。测试证明通知请求正确，未模拟真实平台创建窗口失败或系统通知授权。
- 没有截图证据，未把像素对齐、屏幕阅读器、真实主题对比度声称为通过。

2. 修改 `wall_generator` 枚举，测试 ⌘Z/⇧⌘Z/⌘S；保存预览中 Escape 取消，Enter 保存；检查文件仅有预期变更。
3. 有未保存编辑时 Open 另一目录，取消与确认各一次；关闭窗口和两个窗口下的 ⌘Q，同样验证取消保留、确认放弃。
4. 若出现设置读写错误，检查通知内容、Dismiss 的键盘可达性和修复权限后的重试。

### M10：新建、复制、批量复制、重命名、删除预设

**排在批量编辑之前的原因**：OrcaSlicer 仓库里 Snapmaker 目录近一年改动文件最多的提交，主要是成组新增预设。例如 `d7b00c3e42` 为 U1 加 0.2/0.6/0.8 喷嘴，新增 84 个文件；`b8d4ff25e8` 新增 110 个。这类工作是「把一组现有预设复制成新喷嘴或新机型的版本，再改几个键」，比批量改值更常见。

**范围**
- 复制一个现有预设为新预设：新文件名、新 `name`，可选择继承原预设或和原预设继承同一个父项。
- 批量复制一组预设：按厂商、搜索或机型选出一组同类型的预设（可以包含父项和它的子孙），用一条名称替换规则（例如 `0.4 nozzle` → `0.2 nozzle`）生成新的 `name` 和文件名，并对所有副本统一设置几个键。
- 重命名预设：改文件名、`name` 和厂商索引里的清单条目，并更新引用它的地方（同厂商同类型的 `inherits`；打印机重命名时还有各厂商 `compatible_printers` 里的名字）。
- 删除预设：有子孙继承它、或有列表引用它时先列出这些引用，确认后才删除。
- 新增一款机型（`machine_model`）暂不做。

**关键设计决定**

- **先出计划，再写盘**：core 的 `ManagementPlan`（`manage.rs`）为新建、复制、批量复制、重命名、删除各生成一份计划：文件快照、逐文件的改前改后文本，以及提示。提示分两种：「Cannot apply」阻止写入，「Review」只提醒。生成计划不写 profiles 目录。
- **数组元素级编辑**：`Document` 新增 `array_insert` / `array_set` / `array_remove` / `array_set_member`，改清单条目或 `compatible_printers` 里的一个名字时，其他元素、分隔符、BOM 和 CRLF 逐字节保持不变。M11 的数组追加和移除复用这套能力。
- **过期检测用内容指纹**：`Repository` 加载时记录每个读过的 JSON 文件的内容指纹（缺失或读不了的文件也记下）。生成计划时只要有一个字节变了就要求先 Reload，所以只改了格式也算变化。
- **预览只加载一次**：改后的结果在临时目录里加载一次，没改动的文件用硬链接放进去，不支持时才复制；对比基准直接用已加载的数据。新出现的 Error / Fatal 阻止写入，新出现的 Warning 列出来供检查。重命名会把旧路径映射到新路径，文件原有的问题不会被当成新问题。
- **复制**：新预设写 `from: system`，去掉 `renamed_from`。`setting_id` 和 `filament_id` 默认去掉，也可选择保留，预览里都会提示。新条目追加到清单末尾，所以父项一定在子项前面。OrcaFilamentLibrary 的耗材清单原来为空、靠目录自动发现时，先把它写成显式列表，保持原来的加载顺序。
- **批量复制**：名称替换规则同时生成新 `name` 和文件名（文件名与预设名一致，Snapmaker 现有 543 个预设都是这样）。组内的父项被复制时，新子项继承新父项；不在组内时继承原父项。可选择把替换规则也作用到 `compatible_printers` 和 `compatible_prints`。统一设置的值按「key = value」逐行填写。有预设没匹配到替换规则时整组拒绝。
- **重命名**：一并修改文件名、`name` 和清单条目，并更新所有厂商里的引用：`inherits`、`compatible_printers`、`compatible_prints`、`default_print_profile`、`default_filament_profile`，以及机型的 `default_materials`。同名预设出现在多个厂商时拒绝，因为引用有歧义。可选择把旧名追加到 `renamed_from`（分号分隔），也允许只改文件名大小写。
- **删除**：还有子孙继承所删预设时阻止。其他文件里的名字引用会在预览中逐条列出，确认后移除；如果移除后 `compatible_printers` 或 `compatible_prints` 变成空列表，会让那个预设兼容所有打印机或工艺，因此也阻止。
- **写入**：每个 profiles 目录同时只允许一个窗口写入，用的是进程内的锁，应用崩溃也不会留下锁文件；其他进程的改动靠写入前对快照和每个文件的复查发现。改动先暂存在 profiles 目录下的 `.orca-profile-studio-transaction-*` 里，然后依次处理：先删除，再放预设文件，最后改清单。新文件用硬链接安装，不会覆盖已有文件。任何一步失败都会回滚；回滚也失败时，保留暂存目录和 `recovery.json`，并提示原文件所在位置。
- **界面**：工具栏的「Presets」按钮或命令面板的「Manage presets」打开管理视图，它占用主区域，「Back to browser」返回。选择表格 `PresetPicker` 按类型、厂商、搜索词和打印机型号筛选，型号筛选在后台计算兼容性。选择按文件路径记录，筛选变化后只保留仍显示的行，M11 也会复用这个表格。预览用 `Root` 的 `AlertDialog` 逐文件列出改动，清单数组只显示增删的条目，删除操作的按钮用 Danger 样式。还有未保存的编辑或未应用的输入时不能进入管理视图。写入期间阻止关闭窗口、退出应用、Reload 和打开其他目录；写完后走 M8 的刷新流程。

**测试**：core 覆盖继承和清单顺序、只改所请求的值、重名和非法输入、引用更新时其余字节不变、写入中途失败后完整回滚、过期检测、跨厂商公共库继承、符号链接拒绝、清空兼容列表的阻止、重命名不误报旧问题和只改大小写；真实数据回归在 OrcaSlicer 检出上生成一次预览，确认不写入。headless 界面测试覆盖新建、复制、重命名、删除和批量复制的预览与确认，重名和过期预览，编辑未保存时的拦截，型号筛选与选择裁剪，写入期间的关闭/退出/切换目录保护，以及小窗口中的长预览。`cargo test --workspace` 109 项通过（core 53、真实数据回归 11、桌面 45），clippy 和 fmt 通过。

**已知局限**
- 批量复制的文件名统一按新名字生成，不能逐个修改。
- `compatible_printers_condition` 这类条件表达式里的名字不会跟着改；目前真实数据里没有条件表达式引用预设名。
- 新增机型（`machine_model`）仍不支持。

**手动检查建议**（写入会改动打开的目录，请在 profiles 的临时副本上做）
1. 用「Presets」复制一个 Snapmaker 工艺：预览中 Escape 取消、Enter 写入；检查新文件和清单只多出对应条目。
2. 批量复制：筛选 Snapmaker 并搜索 `0.4 nozzle`，「Select shown」，替换为 `0.2 nozzle` 并勾选替换兼容列表里的名字；检查树里的继承关系和兼容列表。
3. 重命名一个父项并记录 `renamed_from`：检查子项的 `inherits` 和其他厂商里的引用；再试一次只改文件名大小写。
4. 删除：选一个还有子项的父项，以及一个删除后会清空某个兼容列表的打印机，确认两者都被阻止。
5. 缩小窗口检查管理视图和预览的布局，以及键盘和焦点。

### M11：批量编辑

> M16 起键列表来自 profile 实际写过的键，追加 / 移除元素对所有数组值开放，预览的新增问题列改为多余覆盖值。

**范围**：对同类型的一组预设设置或删除一个键，追加或移除字符串数组的元素。可选的「提到父项」推后，不在本次实现范围内。

**关键设计决定**

- **先预览，再应用到编辑会话**：工具栏或 ⌘K 的「Batch edit」打开独立视图；复用 `PresetPicker`，支持类型、厂商、搜索词、打印机型号和问题代码筛选。筛选收窄时裁剪选择，型号计算未完成时不能生成预览。选择、输入、编辑会话或加载快照变化后，旧预览失效；后台计算还带请求编号，应用前再次比较基线。
- **按当前编辑状态解析继承**：预览读取整条链上的未保存编辑。设置值会为每个目标写入本地值；删除键恢复继承。追加/移除仅对 schema 的 `Strings` 类型开放，避免把数值向量的下标含义误当成集合。已有元素不重复追加，移除会去掉所有相同项；没有变化的目标跳过。继承来的数组需要修改时，以它的当前最终值建立本地覆盖，并标为「New override」。
- **预览展示结果和影响**：虚拟表格列出每个目标的前后最终值与来源、新增的 schema 校验问题、变更状态和最终值会变化的子孙数量。父子一起选中时按加载顺序先算父项：子项自己没写这个键、改后的父项已经给出目标值时，标为「Inherits the new value (skipped)」，不再写入多余的覆盖值，以后仍跟随父项；已经继承了目标值的预设算作不变。点预设名可以打开可滚动详情，查看长数组和全部问题。schema 问题供审阅，和 M3 一样不阻止应用；兼容性及其他仓库检查在保存刷新后更新。
- **整批撤销和重做**：`EditSession` 的历史记录带可选组号，`Edits` 按文件路径记录组成员。批量视图的 Undo/Redo 和 Values 页的 ⌘Z/⇧⌘Z 都经过同一入口；撤销前先检查全部成员的栈顶，不允许部分回退。成员有后续单独编辑时提示先撤销后续编辑；某成员历史已因外部变化或明确放弃而丢失时，整组拒绝操作。保存和按路径重载继续保留历史。
- **共用编辑器和保存流程**：`value_editor.rs` 持有 schema 对应的控件。Values 页保留 bool/enum 即时应用、文本 Apply/Enter 的行为；批量视图的输入须先预览再 Apply batch；Set value 的输入从第一个选中预设的当前值开始（选择变化且未改输入时跟着更新），不从 schema 默认值开始，避免未改输入就预览、应用时把整批改成默认值。只有改过的输入才算未应用的输入，单纯选择键或操作不算。`save.rs` 提供同一个保存预览、Enter 确认、Escape 取消和保存后刷新。写入沿用 M3：逐文件保存，失败时报告已保存的部分，不新增另一套事务。未应用的批量输入纳入 Open/关闭/退出保护，返回浏览器后仍保留，Reset input 可明确清除。
- **数组局部改写**：`Document::set` 对数组使用 LCS 匹配保留不变元素，只插入、删除或替换不同的元素；原有转义、其他元素和分隔格式尽量逐字节保留，BOM/CRLF 与其他键不变。数组被清空时整体写成 `[]`，不留多行布局的空行。匹配矩阵超过一百万格时退回公共前后缀算法，限制内存和计算量；重复顶层键沿用原来的逐值替换规则。

**自动验证**：core 覆盖数组增删、空数组、重复项、重排、BOM/CRLF/转义与撤销组；预览模型覆盖已编辑祖先、父子同时变化、跳过、覆盖、新增问题、过期拒绝和分组历史冲突。headless 测试通过真实控件完成三文件设置/保存、数组追加与移除、删除键、筛选裁剪、保存后跨视图撤销/重做、预览失效、未应用输入关闭保护，以及 960×720 大字号布局。所有写盘测试都在临时 fixture 上运行。`cargo test --workspace` 122 项通过（core 56、真实数据回归 11、桌面 55），clippy 和 fmt 通过。

**手动检查建议**（保存会改动打开的目录，请在 profiles 的临时副本上做）
1. 选中一组 Snapmaker 耗材，往 `compatible_printers` 追加一个打印机名：预览中查看长数组详情，确认已包含的预设被跳过；Apply batch 后 Save，检查每个文件只多出这一个元素。
2. 同时选中一个父项和继承它的子项，设置一个值：确认子项标为「Inherits the new value (skipped)」，保存后只有父项文件改动。
3. 移除元素直到某个列表为空，保存后检查文件里是 `[]`。
4. 用 Undo batch / Redo batch 和 Values 页的 ⌘Z / ⇧⌘Z 整组撤销和重做；切换亮暗主题，用 Tab、⌘S 操作，缩小窗口检查布局。
5. 只选键和操作、不改输入时关闭窗口，不应出现丢弃确认；改了输入后关闭，应提示未应用的输入。

### M12：中文界面

> M16 起移除了配置项中文术语（`.po` 读取、中文名称搜索、缺少翻译文件的提示）；界面文字和问题描述的中英文保留。

**关键设计决定**

- **缺少翻译的提示只显示一次**：界面为中文、找不到 `.po` 时提示一次；同一原因在保存或 Reload 后不再重复，明确切换到中文时再提示。
- **PO 解析逐条容错、结果缓存**：遇到不认识的行只丢掉所在条目并计数，不让整个文件失效；解析结果按路径、大小和修改时间缓存，保存后的重新加载不再重复解析。
- **统一语言设置**：`Settings.language` 为 System / English / Chinese，旧设置缺少此字段时默认跟随系统。用 `sys-locale` 读取系统偏好，`zh` 语言映射到 `zh-CN`，其他语言使用 `en`。启动时先设置语言再创建窗口，⌘K 的「Language: … / 语言：…」可切换并保存；原生菜单、应用与 gpui-component 使用同一个 rust-i18n 语言状态，所有窗口一起变化。
- **应用文案集中管理**：`locales/app.yml` 以稳定的语义键保存中英对照，运行时英文兜底。计数文案需要单复数时区分 one/other，撤销与重做使用完整句子，不拼接翻译片段。元素 ID 和配置键/原始值不翻译，无障碍标签随语言变化。已有状态提示保留原文，之后产生的提示使用当前语言。
- **OrcaSlicer 术语在后台读取**：`profile-core::Translations` 解析 `.po`，支持多行字符串、C 转义、上下文和复数首项，跳过 fuzzy、空译文和旧条目。`Catalog` 默认在 `<profiles>/../../localization/i18n/zh_CN/` 查找唯一的 `*_zh_CN.po`；`ORCA_LOCALIZATION_DIR` 可指定 `i18n` 这一层目录。读取失败或候选文件不唯一时显示英文，中文模式给出通知。既不复制翻译文件，也不修改 OrcaSlicer 检出。
- **翻译展示，保留数据**：Values、对比、详情、批量键选择中的名称/类别/说明/单位，以及枚举选项标签使用 PO 翻译；缺译文显示原文。枚举实际值、预设名称、键名、文件名和 schema 类型名保持原样。`SearchIndex::add_option_labels` 加入中文名称，不替换英文；Values/对比筛选也保留两种语言的名称，所以切换语言不会使原搜索词失效。
- **问题描述在界面层翻译**：`issue_text.rs` 穷尽匹配 `IssueKind`，配置校验、继承、清单、兼容性等问题均有中文描述；core 的 Display 和 CLI 保持英文。严重程度和问题面板的选择项也随语言刷新。底层 I/O/解析错误、预设管理 core 提供的技术诊断详情保留原文，外层操作说明和确认按钮已本地化。
- **语言切换不重新加载 profiles**：通过 deferred 更新逐窗口刷新现有视图，重建树标题、表头和下拉选项，并更新输入占位文字。文本控件实体、筛选、选择、编辑会话和撤销记录继续保留；枚举只更新标签而不改已选值。批量预览失效，须按新语言重新生成，已输入的值与选择仍保留。语言切换不调用 `Edits::rebase`，避免正在保存/加载时误判基线。
- **测试隔离**：语言是进程全局状态。只读英文界面的测试拿 `i18n::test_locale()` 的共享锁，可以并行；切换语言的测试拿 `i18n::test_locale_switching()` 的独占锁，进出时恢复英文。启动时 System 偏好走和应用相同的路径，测试里只把「检测到的系统语言」固定为英文（也可设为中文来测 System）。完整性测试检查每个 `t!("…")` 键是否存在、中英文是否齐全、占位符是否一致，以及是否有未使用的资源键。YAML 解析仅作为测试依赖。

**验证**：PO 格式和双语搜索有 core 测试；headless 测试覆盖已保存语言的启动、中文配置项和枚举标签、组件取消按钮、问题描述、英文回退提示、中文搜索、跨窗口同步，以及 Values/对比/批量编辑/预设管理的输入和选择保留；中文 960×720、大字号下检查关键控件边界。`cargo test --workspace` 132 项通过（core 59、真实数据回归 11、桌面 62），clippy 和 fmt 通过。所有写盘测试只使用临时 fixture。中英对照文案可直接在 `locales/app.yml` 审阅；系统字体回退和真实中文显示仍应在窗口中查看。

**使用**：在 ⌘K 中搜索「Language」或「语言」，选择 English、中文或跟随系统。若打开的是独立 profiles 副本，可设置 `ORCA_LOCALIZATION_DIR` 指向 OrcaSlicer 的 `localization/i18n`，随后 Reload 读取术语翻译。

### M13：机型管理

**范围**：从空白新建或复制 `machine_model`，编辑名称、`model_id`、喷嘴规格、系列、技术、热床/贴图/热端资源和默认耗材；支持重命名和删除。新建后自动复制机器预设的一步向导暂不做，后续机器预设复制和兼容列表追加继续使用 M10/M11。

**关键设计决定**

- **机型独立建模，共用事务**：core 新增 `ModelDraft` / `ModelPlan`（`manage/models.rs`），不把机型当作预设草稿。它们生成 `ManagementPlan` 的文件快照、提示与改动，复用 staleness 校验、候选仓库校验、写入锁、暂存和失败回滚。生成预览不写入 profiles。清单数组只修改对应条目，机型文件保留未知字段、BOM 和 CRLF；编辑时只提交实际改动的字段。
- **表单写回保持文件原样**：默认耗材按文件里写的顺序显示和保存（加载结果按 OrcaSlicer 的规则排序去重，只用于判断）；清空的字段直接删掉这个键，不留空字符串。新建或复制的机型必须填写 `model_id`，现有机型缺少时只提醒。重命名时，如果旧名字的封面图还在，预览会提示自己改名，工具不移动图片。
- **名称与引用**：清单的机型名称是 `printer_model` 的目标，`model_id` 是另一个标识。新建/重命名统一文件内 `name` 与清单名称。重命名只更新同厂商机器文件里实际写出的旧 `printer_model`，保持字符串/数组形态，继承的子项跟随父项而不新增覆盖；机器预设自身的名字不变。目标名称、文件名冲突，以及同厂商重复的非空 `model_id` 会阻止写入。
- **删除和变体保护**：有机器预设（包括模板和继承引用）仍引用机型时禁止删除。改喷嘴规格时逐个列出不再有效的 `printer_variant` 并阻止写入。空变体列表、非法字段/文件名和 SLA 技术同样不允许；默认耗材找不到、`model_id` 为空时给出审阅提示。分号列表只接受普通文本，规范化首尾空白，暂不支持 C 引号/转义。
- **资源按真实查找规则提醒**：热床和贴图先查 OrcaSlicer 用户目录，再查内置厂商目录；热端还有 `profiles/hotend.stl` 回退，设置向导封面还有 `resources/web/image/printer/` 回退，详见规格文档 4.1。工作台只检查打开的副本及可定位的内置回退；缺文件仅在操作预览中提醒，不新增全仓库 Issue。图片和模型文件均不复制、生成或删除。
- **界面入口**：预设管理顶部「机型管理 / Machine models」，或 ⌘K 同名命令。来源机型可搜索，操作分为新建、复制、修改/重命名、删除；首次进入沿用当前选择的机型/厂商。表单与文件预览分开，预览复用 M10 的 Root 对话框，Enter 确认、Escape 取消。中文文案、语言切换和大字号布局沿用 M12。
- **保护未完成工作**：有预设编辑或未应用输入时不能进入机型写入流程；机型表单返回浏览器后仍保留。未应用表单纳入 Open、关闭与退出保护，切换来源/操作前须应用或 Reset input。Reload 保留输入；若来源机型变化，提示重置后再预览，避免覆盖外部修改。预览带请求编号，写入前复查文件；写入期间禁止关闭、退出、Reload 和换目录。成功后走 M8 的后台刷新。

**验证**：core 覆盖创建/复制/修改/重命名/删除、未知字段与格式保留、继承引用、重复与无效输入、资源回退提示、清单大小写、过期拒绝及失败回滚；headless 测试通过真实控件完成各操作，验证显式确认、引用/变体阻止、过期预览、语言切换与外部修改、关闭保护和小窗口布局。所有写入使用临时 fixture。`cargo test --workspace` 145 项通过（core 67、真实数据回归 11、桌面 67），clippy 和 fmt 通过。

**手动检查建议**：在 profiles 临时副本中复制一个机型，设置新的名称和 `model_id`，查看资源提示后写入；再用 M10 复制机器预设、用 M11 更新兼容列表。检查文件 diff、中文表单和键盘操作。技术诊断详情沿用 core 的英文，操作文案与按钮支持中英文。

### M14：多余覆盖值检测与提到父项

> M16 起只有不带 schema 的结果（56,926 项），Python 脚本的 schema 参数已删除。

**关键设计决定**

- **按当前编辑判断、不碰共享库**：Values 页的提示按父项当前（含未保存编辑）的最终值判断，避免照提示删除后最终值改变；有 schema 时只比较属于该类型的键。父项在 OrcaFilamentLibrary 时禁止提到父项，因为它被所有厂商的耗材共用。
- **精确比较，不自动修复**：`IssueKind::RedundantOverride`（代码 `redundant-override`，info）表示子预设自己的某个值与父项的最终值完全相同。按 `RawValue` 比较，不把字符串和单元素数组当成相同值，也不归一化数字拼写或数组顺序。有 schema 时计入经父项继承的默认值；根预设与父链不完整的预设不报告。跨厂商继承可以报告，但检测永远不写文件。
- **独立统计校验**：在 OrcaSlicer `953509c23f` 上，不加载 schema 时是 **56,926** 项，加载 bundled schema 时是 **73,253** 项。Rust 回归断言与 Python 参考脚本独立解析、整键继承后的统计一致。参考脚本新增可选第二个参数 `schema.json`，只为该项统计补入默认层；原有格式和 schema 检查计数不变。
- **纯 core 提升计划**：`PromotionPlan` 接收所选预设、键名，以及每个预设的当前自有值（含编辑会话），只生成修改和影响列表。至少两个不同文件的兄弟预设，必须有同一个直接父项、相同类型、完整继承链，且各自写有完全相同的值。父项属于另一个厂商时拒绝，包括跨厂商引用 OrcaFilamentLibrary。父项已写相同值时不改它，只删除子项覆盖。
- **看全影响再应用**：批量编辑新增「提到父项 / Promote to parent」，直接读取所选子项的共同值，不另给一个新值输入框。预览包含父项、所选子项、每一个最终值会变化的未选子孙，展示前后值、来源和角色。未选子孙只是影响行，不在写入列表；顶端明确显示影响数量。其他子孙已有覆盖、或因所选子项保持原最终值而不受影响时不列入。
- **沿用 M11 会话与撤销组**：`BatchPlan` 使用 core 计划，应用前仍验证整个编辑基线，生成一组父项设置加子项删除的修改。父项若实际变化也加入同一撤销组；任何成员有后续单独编辑时整组拒绝撤销，避免部分回退。Save 继续使用 M3 的预览和逐文件保存，M8 刷新保留组历史；未选子孙文件不写入。
- **问题与中文支持**：问题面板选“所有级别”后可按 `redundant-override` 筛选，并定位到对应键；Values 的键详情也显示该提示。新增操作、角色、限制和影响摘要均有中英文。选择变化、编辑或 Reload 后预览照常失效。

**验证**：core 测试覆盖父链/default 比较、字符串/数组形态和顺序、相同父值、未保存覆盖、未选子孙/屏蔽分支、非兄弟/缺值/跨厂商/断链拒绝；headless 测试覆盖影响预览、无新值输入框、保存后最终值、未选文件逐字节不变、从 Values 整组撤销/重做，以及 info 筛选和中文操作。所有写盘都使用临时 fixture。`cargo test --workspace` 156 项通过（core 74、真实数据回归 11、桌面 71），clippy 和 fmt 通过。

**使用**：在批量编辑中按厂商和名称筛选兄弟预设，勾选后选键和“提到父项”，检查预览中父项及未选子孙的前后值，再 Apply batch、Save。检查多余覆盖值时，在问题面板将严重程度设为“所有级别”，选择 `redundant-override`。移除覆盖会让子项跟随后续父项修改，因此工具只提示，由用户决定是否操作。

### M16：移除 schema

**范围**：`schema.json` 是从 OrcaSlicer 源码导出的配置项"字典"（类型、默认值、取值规则、名称和说明）。把它编译进程序，等于让工具和某个 OrcaSlicer 版本强绑定，导出程序也只在 OrcaSlicer 的本地分支上。讨论过"改为可选的外部文件"和"从 OrcaSlicer 源码生成"之后，用户决定**整个项目不再使用 schema**：工具只分析 profile 文件本身，仓库里不放任何从 OrcaSlicer 导出或复制的文件。

**移除的内容**
- 数据和代码：`crates/profile-core/schema/`、`schema.rs`、`check.rs`（值校验）、`legacy.rs`（`handle_legacy` 的移植）、`po.rs`（`.po` 读取）；`Repository::load_with_schema` 和 `Origin::Default` 默认值层。
- 依赖 schema 的问题类型：未知键、过时键、改名键、不属于该类型的键、标量写成数组、`nil`、数值 / 元素解析失败、枚举 / 布尔被替换、多余文本、超出范围，以及对应的 `schema_*` 回归测试和 Python 脚本的 schema 模式。
- 界面上依赖 schema 的部分：配置项名称、类别、说明、单位和类型说明；勾选框和枚举下拉；"隐藏默认值"筛选；M12 的配置项中文名称和缺少翻译文件的提示。界面本身的中英文不受影响。
- Codex 先做过一版"可选能力"（外部 schema / `.po`、能力面板、`--schema` / `ORCA_SCHEMA`），没有提交，按这次的决定整体放弃。

**关键设计决定**

- **最终值只算到 profile 文件**：整条继承链都没写的键不出现在 Values、对比和详情里，对比中一侧没有的键显示为"（缺失）"。`Edits::effective` 没有默认值兜底，批量编辑的"删除键"在没有父项提供值时显示为"（未设置）"。
- **按键名展示**：Values 表只有键、值、来源三列，对比表是键、左右值、左右来源五列，都按键名排序；筛选和命令面板的配置项搜索只匹配键名。详情页的重点值以键名为标签。
- **编辑控件按值的形态选择**：`ValueEditor` 自己从当前值推断：含换行的文本用多行输入框；其余单个字符串用单行输入框，数组每行一项。布尔和枚举都按普通文本编辑。
- **批量编辑**：键列表是这一类预设（含未保存编辑）实际写过的键；预设元数据（`name`、`inherits` 等，`PresetMeta::is_key`）不能作为键。追加 / 移除元素对所有数组值开放，遇到不是数组的值时按预设报错。预览的"新增问题"列改为显示新出现的多余覆盖值（相对各自父项的当前编辑状态）。
- **多余覆盖值（M14）**：只和父项的最终值比较，不再排除"不属于该类型"的键；回归数字是 **56,926**，Python 参考脚本独立得到同样的结果。
- **兼容性条件的变量按文本推断类型（M6）**：整数按 int，带或不带 `%` 的数字按 double，其余按字符串；未设置的变量是空字符串；不带下标的数组如果所有元素相同，读作这个元素（OrcaSlicer 的单值 vector 就是这样被比较的）。布尔比较把 int 0/1 当作 false/true。用 `Snapmaker_Orca_compat_export` 在 OrcaSlicer `ba538f3bc1`（profile 数据与 `953509c23f` 相同）上重新对照：耗材 2906 项、工艺 2156 项，**0 处差异**。
- **问题与键的关联**：`dangling-compatible-printer` 现在带键 `compatible_printers`，在问题面板里选中它会打开 Values 页并定位到这个键（原来这个用例靠已移除的值校验问题）。
- **CI**：去掉 `source_commit` 一致性和带 schema 的统计核对，数据检出只取 `resources/profiles`。

**验证**：143 个 Rust 测试（core 64、真实数据回归 8、studio 71）通过，clippy 无警告；Python 参考脚本 `--check` 通过；兼容性对照 0 处差异。

**范围**：`scripts/bundle-macos.sh` 生成可以双击启动的 `Orca Profile Studio.app`（`--install` 复制到 `~/Applications/`）。同时完成 M18 在 Mac 上就能做和测的准备：快捷键、菜单、设置文件位置和清单 `sub_path` 不再假设只有 macOS。

**关键设计决定**

- **仓库内脚本打包**：不依赖额外的 cargo 子命令。脚本做 `--locked` release 构建，按 `cargo pkgid` 的版本号写 `Info.plist`（Bundle ID `org.orca-profile-studio.app` 与代码里的 `set_app_identity` 一致；`CFBundleLocalizations` 列出 en / zh-Hans，让系统对话框跟随系统语言；最低 macOS 11），用 `sips` / `iconutil` 从 1024×1024 的 PNG 生成 `.icns`，最后做 ad-hoc 签名并校验。只写 `target/`（`--install` 除外）；不做公证和分发。
- **图标**：`crates/profile-studio/resources/icon.png` 是提交在仓库里的源文件，由 `scripts/icon.swift`（CoreGraphics，无第三方依赖）绘制：圆角方块上叠三层菱形，表示继承链。源文件缺失时脚本先在 `target/` 里重新绘制一张。
- **系统通知**：GPUI 只在主 bundle 有 Bundle ID 时启用 `UNUserNotificationCenter`（否则系统会直接终止进程），所以 `cargo run` 永远不投递，`.app` 才会投递；第一次发通知时请求授权。应用只在没有窗口能显示错误时使用系统通知，窗口内的错误通知不受影响。
- **启动目录**：从 Finder 启动没有终端环境变量，按"上次的目录 → 编译时旁边的 OrcaSlicer 检出"打开；后者是编译时的源码路径，`.app` 拷到别的机器上会失效。空的 `ORCA_PROFILES_DIR` 当作未设置；旧版 macOS 从 Finder 启动时传入的 `-psn_…` 参数被忽略。
- **快捷键**：所有绑定改用 `secondary-`（macOS 上是 ⌘，其他平台是 Ctrl）。工具栏提示里的快捷键不再写死 ⌘，而是用 `i18n::shortcut` 按平台格式化（⌘K / Ctrl+K）。测试也按 `secondary-` 发送按键，在 Windows 上会落到 Ctrl，与 gpui-kit 输入框在非 macOS 平台上的 Ctrl+A 全选一致。
- **菜单和退出**：macOS 把 Quit 放在应用菜单；其他平台在 File 菜单末尾放 Exit（同一个 `Quit` 动作，同样检查所有窗口的未保存编辑）。关掉最后一个窗口时退出，所有平台相同。
- **设置文件位置**：`settings_path(os, var)` 是不读真实环境的纯函数，三种平台在任何机器上都能测：macOS `~/Library/Application Support`，Windows `%APPDATA%`（不回退到 `HOME`），其他平台 `$XDG_CONFIG_HOME`，否则 `~/.config`；`ORCA_STUDIO_SETTINGS` 优先，空值当作未设置。
- **清单 `sub_path`**：`profile-core` 的 `sub_path` 模块集中处理。写回清单时一律用 `/` 连接路径组件；加载时把 `sub_path` 转成本平台的路径形式；查找清单条目按路径组件比较（`filament//a.json` 与 `filament/a.json` 视为同一个）；大小写不敏感的查重用 `/` 形式的小写字符串，不受分隔符影响。新建、复制、重命名预设和机型都走这套规则。

**验证**：147 个 Rust 测试（core 66、真实数据回归 8、studio 73）通过，clippy 无警告，Python 参考脚本 `--check` 通过。新增的测试覆盖快捷键格式、三种平台的设置路径、`sub_path` 的写回与比较，以及嵌套目录中复制、重命名预设后清单只出现 `/`；只在 Windows 上编译的反斜杠测试留给 M18 的 CI。脚本在本机生成 `.app`，签名校验通过；用 `open` 启动（与双击相同，没有终端环境）时，LaunchServices 识别到 Bundle ID，主窗口按记住的尺寸打开。窗口内容和真实系统通知的显示由用户验证：系统通知只在没有窗口能显示错误时才会出现。

### M18：Windows 版

**范围**：在 GitHub Actions 的 Windows 机器上用 MSVC 编译整个 workspace，跑通全部测试（含真实数据回归和 headless 界面测试），并打包成免安装 zip：带图标和版本信息的 `Orca Profile Studio.exe` 加一份中文使用说明。修掉只在 Windows 上出现的路径问题。

**关键设计决定**

- **不交叉编译**：GPUI 的构建脚本要用 Windows 的资源编译器，Mac 上只能对 core 和 CLI 做 `cargo check --target x86_64-pc-windows-msvc`。CI 的 `windows-2025` 任务做 clippy、全部测试（`--no-fail-fast`，一次看到所有失败）、Python 统计核对，最后运行打包脚本（zip 不上传）。MSRV 检查也加了 Windows。
- **保留 Git 的换行转换**：Windows 任务不关闭 `core.autocrlf`，profiles 按 CRLF 检出，和一般的 Windows 机器一致；Rust 回归、格式复现测试和 Python 基线都不受影响。Git Bash 会把以 `/` 开头的参数改写成 Windows 路径，所以稀疏检出规则写成 `resources/profiles/`（中间有 `/` 的规则本来就相对仓库根目录）。
- **不出现 `\\?\` 路径**：打开目录和预设管理改用 `dunce::canonicalize`。`std::fs::canonicalize` 在 Windows 上返回 verbatim 路径，界面和设置文件里会显示 `\\?\C:\…`，而且这种路径不接受 `/`，原来会让机型封面图的回退路径检查失效；那里的拼接也改成按路径组件。
- **硬链接不可用时复制**：事务写入优先用硬链接原子地安装文件（NTFS 支持）。FAT/exFAT 和部分网络盘不支持硬链接，这时改为新建文件（`create_new`）再写入，同样不会覆盖已有文件；回滚也走同一个函数。两种路径都有测试（硬链接通过注入的函数模拟不可用）。
- **exe 资源**：`build.rs` 只在目标是 Windows 时运行，把图标（资源 ID 1，GPUI 也用它作窗口图标）和 `VERSIONINFO` 写成 `.rc` 放到 `OUT_DIR`，用 `embed-resource` 编译，版本号取自 `Cargo.toml`。宏传字符串到 `rc.exe` 时引号容易出错，所以直接生成文本。`.ico` 由 `scripts/icon-windows.sh` 从 macOS 图标 PNG 裁掉外边距后生成（16–256 px），提交在仓库里。release 版用 `windows_subsystem = "windows"`，不弹控制台；debug 版保留控制台以便看 stderr。
- **打包脚本**：`scripts/package-windows.ps1` 兼容 Windows PowerShell 5.1，按 `rustc` 的 host 生成 `orca-profile-studio-<版本>-windows-<x64|arm64>.zip`，只写 `target\`，最后核对 exe 里的版本号。使用说明 `README.txt` 带 BOM 和 CRLF（`.gitattributes` 里设为 `-text`，各平台检出都按原字节），旧版记事本也能正确显示中文。
- **没有菜单栏**：GPUI 在 Windows 上不画原生菜单栏（M17 加的 File 菜单 Exit 在 Windows 上看不到），新窗口、关闭、退出用 Ctrl+N / Ctrl+W / Ctrl+Q，其余操作在工具栏和 Ctrl+K 里；使用说明里写明。安装程序、代码签名和自动更新不做。
- **测试按平台写期望值**：期望值里的相对路径用 `sub_path::to_manifest` 统一成 `/`，界面上显示的路径按 `Path::join` 生成；改相对目录的界面测试把临时目录放在 `target/test-fixtures` 下，因为 Windows 的临时目录可能和工作区不在同一个盘，没有相对路径可达。

**验证**：合并前的 M18 分支在 CI 上全部通过（run 41089875555）：Windows 任务的 clippy、全部测试、Python 统计核对、打包和版本号核对，以及 Linux、macOS 和三个平台的 MSRV 检查。Windows 任务首次运行约 40 分钟（含 release 打包），依赖缓存后会缩短。与「打开目录」入口的改动合并后，本地 152 个 Rust 测试（core 68、真实数据回归 8、studio 76）通过，clippy 无警告；合并后的 CI 结果在提交后查看。用户在自己的 Windows 机器上解压 zip 实际使用的验证在提交之后进行，发现问题单独修复。

### 和 Git 对比

**范围**
- 列出 profiles 目录（OrcaSlicer 检出）里相对 `HEAD` 改动过的预设文件：修改、新增、删除。
- 对每个改动的预设按键显示 `HEAD` 和工作区的值差异，而不是按行的文本 diff；可以从这里跳到对应的预设。
- 命令行也提供同样的功能（例如 `profile-tool changes`）。

**设计要点**
- 调用 `git` 命令行（`git status --porcelain`、`git show HEAD:<路径>`），不引入 libgit2；目录不是 Git 仓库时给出提示。
- `HEAD` 版本的文件按和加载时相同的规则解析成键值，再逐键比较；界面复用 M4 对比页的表格。
- 这是只读功能：不提供暂存、提交、还原等 Git 操作。

**依赖**：M4 的对比视图。

**完成标准**：在临时 Git 仓库的 fixture 里，修改、新增、删除的文件都正确列出，按键差异正确；有 core 测试和 headless 测试。
