OrcaSlicer 的加载语义以 [profile_format_spec.md](reference/profile_format_spec.md) 为准，本文只在需要时引用。

## 已完成

### M0：core 和命令行

**关键设计决定**

- **严格复刻 `load_vendor_configs_from_json` 的顺序语义**：每个厂商单独加载，每一类有自己的名字表，按清单顺序一次扫描完成。不按名字构建全局继承图，否则「父项排在子项后面」这类会让 OrcaSlicer 加载失败的错误就会被掩盖。
- **厂商顺序**：OrcaFilamentLibrary 排第一，其余按字母排序。OrcaSlicer 用的是目录遍历顺序，标准没有规定，这里排序是为了结果可重现。
- **加载从不中断**：所有偏差都记成 `Issue`，分 `fatal` / `error` / `warning` / `info` 四级。`fatal` 专门表示「OrcaSlicer 会因此拒绝加载整个厂商」，这样校验结果和 OrcaSlicer 的实际后果能一一对应。
- **值一律按字符串处理**：`RawValue` 只有字符串和字符串数组两种形态，和 JSON 里的写法一致；类型信息留给后来的 schema（M0.5）。
- 查找用文件里的 `name`，不用清单名或文件名；元信息键名不区分大小写，和 `boost::iequals` 一致；容忍 UTF-8 BOM，但会记一条问题。
- OrcaFilamentLibrary 的清单为空时，按 OrcaSlicer 的规则扫描磁盘生成清单。
- **回归测试锁定 OrcaSlicer `953509c23f` 的统计数字**，并用独立的 Python 参考脚本交叉验证。数据变化时需要有意识地更新这些数字。

### M1：桌面浏览器

**关键设计决定**

- **锁定 `gpui-kit = "=0.8.0"`**：它还没到 1.0，版本之间有破坏性改动。遇到 API 问题时去读 `~/.cargo/registry` 里的源码，不靠猜。
- **加载放在后台线程**：`Repository::load` 和 `Catalog::new` 都在后台执行器上跑。`Catalog` 是只给界面用的索引，包括按厂商分组和每个预设的问题。`TreeItem` 里有 `Rc`，不是 `Send`，所以树节点要回到前台再构建。重新加载时，新结果会覆盖旧结果。
- **树是虚拟化的**：节点 id 里编码了 `Node`（厂商、分组、机型、预设），渲染回调可以直接从 id 还原节点。
- **界面用 headless 测试验证**：这个环境没有录屏权限，截不了窗口。测试用 `#[gpui_kit::test]` 渲染真实界面、模拟点击，再断言状态和元素属性。
- 图标用 `gpui_kit::assets::IconName`，即完整的 Lucide 图标集，应用里注册了 `AllAssets`。

### M0.5：配置项 schema

**关键设计决定**

- **导出程序放在 OrcaSlicer 仓库里**：`src/dev-utils/Snapmaker_Orca_schema_export.cpp`，在 `personal/schema-export` 分支上。它必须链接 libslic3r 才能遍历 `print_config_def`。生成的 `schema.json` 复制到本仓库的 `crates/profile-core/schema/`，用 `include_str!` 内嵌，文件里记录生成时的 `source_commit`。
- **导出三类默认预设的完整内容，而不只是每个配置项的默认值**：默认预设（`PresetBundle` 构造函数里建的那几个）就是「没有 `inherits` 的预设」的起点，其中有几项没法从单个配置项的默认值推出来：多出的 `*_settings_id` 键，以及耗材里被置为 `nil` 的 nullable 值。
- **「哪些键属于哪一类」以默认预设的键为准**：这是 `Preset::remove_invalid_keys` 实际的判断依据，`Preset::*_options()` 列表只是参考。
- **绕开 OrcaSlicer 的一个空指针问题**：`coEnums` 类型的默认值是不带 `keys_map` 的 `ConfigOptionEnumsGeneric`，直接调 `vserialize()` 会段错误。导出程序改用配置项定义里的枚举表来写值。
- **`handle_legacy` 只能手工移植**（`legacy.rs`）：这些规则是代码，不是数据，导不出来。实现时要注意，数组值会经过两次 `handle_legacy`：第一次值为空，只用来确定键名；第二次用拼接后的值。
- **严重级别按 GUI 实际的加载规则 `EnableSystemSilent` 来定**：
  - 标量数值完全解析不了：`fatal`，整个厂商加载失败；
  - 枚举值或布尔值不合法：`error`，会被静默替换成默认值；
  - vector 元素解析不了：`error`，会被读成 0；
  - 数值后带多余文字、非 nullable 数组里有 `nil`、超出界面上的取值范围：`warning`；
  - 未知键：`warning`，OrcaSlicer 会静默忽略；
  - 过时键、改了名的旧键：`info`。
- **`Repository::load` 的行为保持不变**，另外新增 `load_with_schema`。值的来源用 `Origin` 表示，`Origin::Default` 代表来自 schema 的默认预设。
- **性能**：字符串数组（主要是 G-code）不拼接也不转义，因为没有任何检查会用到它们。加上 schema 后，全量加载从约 195 ms 增加到约 230 ms。
- **只报告，不修 OrcaSlicer 的配置数据**：检查发现的数据问题只作为结论报告，这是用户的决定。

### M2：继承链视图

**关键设计决定**

- **`Repository::trace(id)`**：对每个键返回继承链上设置过它的所有层，离预设最近的在前，第一层就是最终值。这是界面「来源层」和「被覆盖的值」的数据来源，后续的 M4 对比也可以直接复用。
- **`IssueKind::key()`**：把校验问题挂到对应的键上，界面可以按键显示问题。
- **预设详情分成 Overview 和 Values 两个标签页**：Values 是一个 `DataTable`，选中某一行时，下方面板列出每一层的值，以及配置项的说明和问题。
- **`ValuesView` 在需要时才创建**：`TableState` 和 `InputState` 的构造需要 `Window`。最初在 `render` 里创建，因为当时树的选择回调里拿不到 `Window`；M5 之后 `StudioApp::new` 有了 `Window`，改为在事件处理函数里创建（`observe_in` 的选择回调、切换标签页、命令面板跳转），符合 gpui-kit Coding Guides「不在 render 里改状态」的要求。值编辑器同样改为在选择或数值变化的处理函数里重建。
- **表格 delegate 持有一份自有的显示行（`ValueRow`）**，不借用 `Catalog`，免得出现自引用的生命周期问题。筛选之后，按键名找回原来选中的那一行。
- 默认排序是先按 schema 的类别、再按配置项名称，schema 里没有的键排在最后。
- **测试经验**：
  - 表格行用 `("row", ix)` 查找；
  - 标签页要在 `within("preset-tabs")` 里按序号点击；
  - 点击触发订阅事件之后，要先 `run_until_parked`，再 `render_frame`，然后才能断言。

### M3：编辑表单

**关键设计决定**

- **按字节范围改写文件，不重新序列化**（`document.rs`）：`Document` 记下每个顶层成员值的字节范围，修改时只替换这一段，新键追加在最后一个成员之后。缩进、BOM、文件末尾有没有换行都保持原样。
  - 替换数组时沿用原值的写法：单行数组保留单行和原来的分隔符（`", "` 或 `","`）；多行数组沿用原来的元素缩进和右括号缩进。新键用文件自己的缩进，按 nlohmann 的多行写法。
  - 字符串转义用 serde_json，和 nlohmann::json 的 `dump()` 完全一致。现有数据里只用到 `\n`、`\"`、`\\`、`\t`，没有 `\u`。
  - 设成和原来相同的值时不改动文本，所以「打开 → 不修改 → 保存」得到的字节和原文件完全相同。
  - 对现有数据的验证：把全部 7935 个文件里的约 19 万个值逐个按原写法重新渲染，只有 4 个数组和原文不同，而且差别只在空白（`[` 或元素后面多余的空格、空数组里的空白行）。测试把这 4 处固定下来。
- **编辑会话**（`edit.rs` 的 `EditSession`）：在预设自己的值上叠加修改，撤销栈记录每一步的前后值。值为 `None` 表示删掉这个键、恢复成继承来的值。`Repository::trace_with` 和 `check_values` 直接基于会话里的值计算，所以表格、来源层和校验问题都会实时反映修改。
- **保存的安全措施**：
  - 保存前把磁盘上的文件和会话最后一次加载或保存的值比对，不一致就拒绝保存（`SaveError::ChangedOnDisk`），绝不覆盖外部的修改；
  - 先写到同目录下的临时文件再改名，失败时不会留下写了一半的文件；
  - 只有用户在确认面板里点「Save N file(s)」才写盘，确认面板会列出每个预设、每个键的前后值。
- **保存后不自动重新加载**：继承被保存预设的子孙预设要重新加载才会更新，状态栏会提示。自动重新加载会让其他预设里还没保存的编辑丢失。
- **编辑放在下方的详情面板里**：gpui-component 的 `TableDelegate` 不支持单元格内编辑。控件按 schema 类型选择：
  - bool：复选框；
  - enum：下拉框。可选值取自 `enum_keys`，也就是加载时接受的值，显示名用 `enum_values` / `enum_labels`。Snapmaker 特有的 `enum_values_u1` / `enum_values_ex` 只有 `curr_bed_type` 用到，而且只影响界面显示，所以不采用；
  - 单个值：单行输入框，按回车或点 Apply 生效；
  - 数组：多行文本框，一行一个元素；
  - G-code 等多行字符串：多行文本框，内容原样编辑。由多个多行元素组成的数组，一个文本框表示不了，只提示到文件里去改。
  - **修改保持值原来的形态**：字符串还是字符串，单元素数组还是数组（现有数据里有 74880 个单元素数组），这样 diff 只有值本身的变化。
- **编辑状态放在应用层的 `Edits` 实体里**：每个预设一个会话。切换预设不会丢失编辑，树上会给有未保存修改的预设加铅笔图标。重新加载或打开别的目录时，第一次点击只给出警告，再点一次才会丢弃编辑。
- **快捷键**：⌘Z 撤销、⇧⌘Z 重做、⌘S 打开保存确认，作用范围是 `ValuesView`。焦点在输入框里时，输入框自己的撤销优先。

### M4：预设对比

**关键设计决定**

- **`Repository::diff` / `diff_with`**：对两个同类型预设的 `trace` 求键并集，保留两边完整的继承层；支持跨厂商，类型不同返回 `DiffError`。`diff_with` 接受两边各自的编辑会话值，祖先仍使用加载时的快照，与 Values 页一致。
- **按原始有效值比较**：使用 `RawValue` 相等性，区分字符串和数组、数组元素顺序以及数值字符串的写法。缺失值不同于空字符串或空数组。来源不参与值是否相等的判定，但两边来源都保留。
- **入口采用 Values 页的「Compare with…」**：可搜索的选择器只列出其他同类型预设，包含模板和跨厂商预设，显示厂商、名称和路径以区分重名。此阶段采用这个入口，树的右键快捷入口留待后续交互完善。
- **独立的只读 `CompareView`，沿用 Values 的表格与来源层展示方式**：列出类别、名称、键、左右值和左右来源，默认只看差异，可以搜索和排序，选中键后查看两边的继承链。数组显示方括号，避免把数组和字符串的差异隐藏掉。
- **观察共享的 `Edits` 实体**：任一边的编辑变化都会刷新对比；标题标明未保存修改。返回 Values 后保留编辑器、筛选和选择，对比本身不写文件。
- **Headless 测试验证实际交互**：选择器搜索、选择预设、差异筛选、来源展开、编辑刷新和返回 Values。选择器根节点会填满父容器，需显式限制高度，避免挤掉表格。
- **真实数据验收**：`Generic ABS @U1 0.2 nozzle` 对比 Snapmaker 的 `Generic ABS`（实际的 0.4 nozzle 预设名），最终值仅 `compatible_printers` 不同。core 回归测试与 headless 界面测试均覆盖这一案例。

### M5：全局搜索和命令面板

**关键设计决定**

- **线性扫描，不建倒排索引**（`search.rs` 的 `SearchIndex`）：所有预设文件里写的值一共约 25 万个、7.5 MB 文本。索引只存小写副本，加载时在后台和 `Catalog` 一起构建；release 构建下建索引约 37 ms，每次查询 2–3 ms，所以每输入一个字符就同步搜一次，不需要后台查询。
- **搜三类内容**，查询里的每个词都必须出现（不区分大小写）：
  - **预设**：名称、别名、`setting_id`、`filament_id`（用 `Repository::filament_id`，和 OrcaSlicer 的取值顺序一致）。排序：名称以查询开头的在前，可选预设在模板前，名称短的在前；
  - **配置项**：schema 里的键名和名称；
  - **值**：只搜文件里直接写的值，不搜继承来的和默认值，否则每个值会在所有子孙预设里重复出现。匹配的文本是 `key = value`，所以 `nozzle_temperature 270` 能找到「哪些文件把它设成 270」。结果片段保留原文的大小写，多行内容压成一行。
- **只搜加载时的数据**：未保存的编辑不在索引里，保存后要 Reload 才能搜到。
- **一个面板同时放命令和搜索结果**：用 gpui-component 的 `Command`，设 `filterable(false)`，由应用根据 `on_query` 自己生成分组：Commands、Presets、Options（只在选中了预设时出现）、Values set in files，每组最多 8 条，标题里显示总数。`on_confirm` 给出的 `IndexPath { section, row }` 对应到应用记下的目标；空的分组不显示，所以目标表和分组是一起生成的。
- **面板放在 `Root` 的对话框里**（`window.open_dialog`）：遮罩、焦点锁定、Esc 和点击外部关闭、关闭后恢复原来的焦点，都由 `Root` 负责，符合 gpui-kit Coding Guides 对模态层的要求。对话框的构建函数可能被反复调用，所以它只读取应用里的数据，初始聚焦用一次性的标记。
- **不在 render 里改状态**：分组和目标表在打开面板时和查询变化时（`on_query`）重新生成，render 只读取。debug 构建下一次搜索约 30 ms，放在 render 里会随每次悬停重复执行。
- **跳转**：`TreeState::set_selected_item` 会展开所有上级节点并选中，`reveal_item` 再滚动到这一行；跳到值或配置项时切到 Values 页，把表格筛选到这个键并选中。
- **快捷键需要焦点**：没有任何元素获得焦点时，⌘K 不会被分发。`StudioApp::new` 现在接收 `Window`，创建时把焦点给根元素，并用 GPUI 的 `on_focus_lost` 在焦点所在的元素消失（比如重新加载后视图被替换）时把焦点收回根元素，而不是在 render 里请求焦点。
- 命令行也有 `profile-tool search <查询>`，输出三类结果和耗时。

### M6：校验结果面板和条件表达式

**关键设计决定**

- **条件表达式只实现用得到的那部分语法**（`condition.rs`）：现有数据里有 97 个工艺预设、29 种不同的条件，全部来自 Prusa，只用到变量、`[下标]`、`=~` / `!~` 正则、`==` 和 `and`。实现时补齐了 `PlaceholderParser` 布尔表达式这一层：`or`/`||`、`and`/`&&`、`not`/`!`、括号、`==`、`!=`/`<>`、`<`、`>`、`<=`、`>=`、字符串、`true`/`false`。四则运算和 `if` 块不支持，遇到时报「无法解析」。
- **语义对照 C++ 源码**：
  - `=~` 是 `boost::regex_match`，必须匹配**整个**字符串；Boost 默认的 Perl 语法里 `.` 也匹配换行，而 40 个带 `PRINTER_…` 的打印机 `printer_notes` 全是多行。所以正则编译成 `(?s)^(?:pattern)$`；
  - `==` 比较两个数时，只要有一边是浮点数就按 1e-8 的容差；两边有字符串时按字符串比较；布尔值只能比较相等；
  - `and` / `or` 两边都会求值，和 C++ 一致。
- **变量**：取目标预设的最终值（包括 schema 默认值），按 schema 的类型转成布尔、整数、浮点数或字符串；打印机额外提供 `printer_preset` 和 `num_extruders`，和 `is_compatible_with_printer` 一致。vector 不带下标、下标越界、未知变量都是求值错误。
- **兼容性规则**（`compat.rs` 的 `CompatibilityIndex`，加载完成后构建一次，存在 `Repository` 里）：按规格文档第 6 节的顺序判断，结果带上原因（`Verdict`：被排除、条件、在列表里、不在列表里、没有限制）。条件只在 `compatible_printers` 为空时生效；条件出错时按 OrcaSlicer 的做法视为兼容。公共耗材库的排除机制按别名匹配，同一别名有多个库耗材时取最后一个，和 C++ 的 map 写法一致。也支持耗材与工艺之间的 `compatible_prints` / `compatible_prints_condition`（现有数据没有用到）。
- **条件出错记成问题**：解析失败是 `condition-invalid`，对部分预设求值失败是 `condition-failed`（附第一个失败的例子和失败数量），级别都是 error。现有数据里两者都是 0。
- **性能**：先测再优化。加了兼容性计算和条件检查后，release 加载从约 230 ms 到约 265 ms，没有为此加缓存。界面里预设的兼容性摘要在选中预设时计算一次，不在 render 里算。
- **问题面板放在窗口底部**：按 gpui-kit Design Guides 的「先从任务出发」，主任务是在全部问题里筛出要紧的，再跳到对应的预设和键。面板是可调高度的底部区域（类似 IDE 的 Problems），上方的树和详情跟着选中的问题变化。
  - 筛选：最低严重级别（默认「warning 及以上」，因为 4105 条 info 大多是过时键之类的噪音）、问题代码、厂商，都是 `Select`，代码和厂商可搜索并带数量；另有文本筛选。
  - 选中一行（点击或方向键）就跳到对应的预设；问题涉及某个键时打开 Values 页并定位到这个键。键盘焦点留在列表里，可以一直用 ↑↓ 浏览。没有对应预设的问题（比如孤立文件）跳到厂商节点。
  - 严重级别同时用图标和文字表示，不只靠颜色；入口是工具栏的「Issues」按钮（打开时显示为选中状态）和命令面板的「Show issues」。
- **兼容性显示在预设的 Overview 里**：耗材和工艺显示条件（如果有）和兼容的打印机（前 12 个加剩余数量）；打印机显示兼容的工艺和耗材数量。命令行有 `profile-tool compat <预设名>`，列出每台打印机兼容的原因。
- **还没做到的完成标准**：兼容性结果还没有和 OrcaSlicer 对照。对照需要从 OrcaSlicer 导出一张兼容性表，这要改 OrcaSlicer 仓库，需要用户同意。目前的回归测试固定的是本实现在真实数据上的结果（例如 Snapmaker U1 0.4 兼容 16 个工艺、169 个耗材，库里的 Generic ABS 对 796 台打印机中的 68 台被排除）。

## 后续阶段

### M7：可停靠布局、主题、多窗口

**范围**
- 用 gpui-component 的 `dock` 模块，把树、详情、问题面板、对比视图做成可停靠的面板，布局可以保存和恢复。
- 支持亮色和暗色主题切换。
- 支持多窗口。

**设计要点**：多个窗口共用一个 `Repository` 的 `Arc`，还是每个窗口各自打开一个目录，到时再定。

**依赖**：M3–M6 做出来的各个面板。

**完成标准**：布局能保存并恢复，有对应的测试；切换主题后界面颜色正确。

### 扩展：2D G-code 分层查看器

**范围**：打开一个 G-code 文件，逐层查看 2D 的走线路径。这主要是练习 GPUI 的自定义绘制。

**设计要点**
- 在后台解析 G0、G1、G2、G3 指令，以及换层标记（`;LAYER_CHANGE` 或 Z 值变化）。
- 用 GPUI 的 canvas 和 path 绘制；大文件按层分块加载。

**完成标准**：能打开 OrcaSlicer 导出的 G-code，逐层浏览，缩放和平移流畅。
